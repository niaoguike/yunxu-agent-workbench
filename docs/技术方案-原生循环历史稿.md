# 一站式需求交付 Agent 平台：技术方案

状态：历史技术候选方案，尚未实现或实测。产品行为以 `docs/PRD.md` 的当前草案及后续确认为准；本文早先的三类固定交付范围、静态页面限制和部分默认参数尚未按新 PRD 全面协调，不作为已确认要求。模型版本、预算与质量阈值仍须通过基准实验标定，不将初始值表述为实验结论。

执行内核已单独确认采用 Python 原生 Agent 工具循环 + LangGraph，见 [ADR-0001](adr/0001-python-agent-runtime.md)。这项确认不使本文其他历史候选自动成为已定架构。

## 1. 产品定义与交付范围

用户通过自然语言提交需求和材料，平台完成需求澄清、任务规划、工具执行、成果生成、验收与修复，交付文件及可核查的执行证据。

首个完整版本支持三类任务：公开资料研究（Markdown 报告及来源）、上传 CSV 的数据分析（分析报告、图表、结果 CSV）、基于资料的静态展示页（HTML/CSS/JS 及预览）。三类任务共用执行内核，通过交付模板定义工具权限、产物格式和验收器。静态页面不包含用户后端或任意服务部署。

示例：上传销售 CSV，要求按地区分析趋势，结合提供的行业资料解释变化，输出分析报告、图表和一个展示页面。缺少行业证据时明确标记推测，不编造因果关系。

版本范围不包含桌面控制、移动客户端、任意第三方写入、插件市场和自主训练。平台通过 Web 使用，执行发生在云端隔离环境。借鉴 Cindy 的任务交付、Skills 与工具整合理念，自行设计云端内核，不假定其公开客户端包含后端实现。

## 2. 设计方法

按“用户需求 → 交付契约 → 失败模式 → 执行机制 → 验收证据 → 对照评测”设计。每个模块都必须对应一种可观察的问题，并有通过其公开接口验证的方式。

确定性的职责交给程序：身份验证、参数校验、权限、预算、状态转换、依赖检查、重试上限、文件检查。需要语义判断的职责交给模型：澄清、拆解、选择工具、分析观察结果、提出修复。

整体采用外层状态图和内层 Agent 工具循环。外层决定允许进入哪些阶段，内层根据实际结果选择下一步动作。LLM 无权直接写入“任务成功”状态。

## 3. 架构与技术栈

```text
React Web ── REST / SSE ── FastAPI
                             │
                      PostgreSQL
                 任务/租约/事件/检查点
                             │
                      Python Worker
                      LangGraph 内核
                    /        |        \
              模型调用    工具执行模块    验收模块
                           /      \
                    内置工具     MCP 工具
                           │
                    隔离执行模块
                           │
                      对象存储
```

| 选择 | 用途及取舍 |
| --- | --- |
| Python 3.12、FastAPI、Pydantic | 模型与数据处理生态；统一输入输出校验 |
| LangGraph、PostgreSQL checkpointer | 状态图、条件分支、人工中断与恢复；业务任务状态仍由应用管理 |
| PostgreSQL、SQLAlchemy、Alembic | 业务数据、事件、任务调度和迁移；初始部署无需 Redis/Celery |
| React、TypeScript、Vite | 任务工作台、执行时间线、文件预览 |
| S3 兼容对象存储 | 原始材料、抓取快照、产物及运行清单；本地可用 MinIO |
| pandas、Matplotlib | CSV 分析和静态图表，运行于隔离环境 |
| Playwright | 静态页面截图、基础交互与浏览器错误检查 |
| Docker Compose | 应用部署；执行宿主与应用数据、凭据分离 |
| pytest、Playwright、结构化日志 | 内核测试、端到端验证和故障定位 |

以一个支持原生工具调用、结构化输出的模型作为基线。模型接入统一为 generate(messages, tools, output_schema)，只实现真实使用的提供商适配器与测试用假实现。模型 ID、采样参数、价格表版本随运行记录固定。具体模型由基准任务的质量、成本和延迟选择，不能仅凭参数规模提前定论；不默认按角色接入多个模型。

## 4. 用户流程与交付契约

流程：创建任务并上传材料 → 展示需求和默认假设 → 缺少关键条件时提问 → 形成计划 → 执行与实时观察 → 验收与有限修复 → 查看或下载产物。

TaskSpec 包含 goal、inputs、deliverables、acceptance_criteria、constraints、assumptions、budget、version。每条验收条件具有稳定 criterion_id、检查方式、必要性和目标产物。用户已明确的要求不重复确认；关键缺失才阻塞执行。

需求变更生成新 TaskSpec 版本，保留旧版本。Worker 在安全点应用变更，重新检查受影响计划与成果；旧版本验收结果不能证明新版本已经完成。

## 5. Agent 规划与执行

采用层级规划与有界 ReAct：先生成可验证的子任务 DAG，再由执行 Agent 对每个就绪子任务进行“观察 → 选择动作 → 调用工具 → 读取结果”的循环。日志保存简短行动说明、工具参数与结果，不保存或要求模型输出隐含思维链。

子任务字段：id、objective、depends_on、input_refs、expected_outputs、acceptance_ids、allowed_tools、status、attempts。程序校验 DAG 无环、依赖存在、每个必要验收条件被覆盖。计划描述不能增加权限。

每轮动作只能是调用工具、提交子任务结果、请求澄清、请求重规划或报告无法继续。子任务完成需要结果引用和适用检查通过。模型返回非法结构时允许一次纠正，再失败则记录明确错误。

触发重规划：前提被证据推翻、关键输入不可获取、工具持续失败、验收发现计划遗漏、用户修改需求。普通网络重试不触发重规划。新计划记录版本和变更理由；有效产物可复用，依赖无效产物的下游任务重新执行。

默认单个执行 Agent；允许最多两个互不依赖的研究子任务使用独立上下文并行执行。子 Agent 只收到子任务、最小输入、权限子集和预算；返回摘要、证据与产物引用，不共享可写工作区。主 Agent 合并冲突，验收阶段单独调用模型审查。此设计不采用多个角色自由聊天；是否开启并行由同预算评测决定。

初始保护参数：单子任务最多 12 次工具动作、总计 60 次、最多 2 次重规划、2 轮验收修复、2 个并行子任务。参数均可在任务配置中下调，硬上限由服务端控制；这些是初始配置，不是最优值。

## 6. 工具执行与 MCP

工具执行模块唯一入口 execute(tool_name, arguments, execution_context)。调用方无需自行处理参数、权限、超时、记录和输出截断。

工具定义包括 name、description、input_schema、output_schema、side_effect_class、timeout、max_output_bytes、required_permissions。返回 ToolResult：ok、data_ref、summary、error_code、retryable、elapsed_ms。大结果进入对象存储，模型只获得摘要与按需读取引用。

内置工具：search_web、fetch_page、read_file、write_file、run_python、render_page、capture_page。搜索摘要只用于发现来源，关键结论必须读取正文。执行工具使用 argv 或类型化请求，不拼接宿主 shell。路径归一化后检查工作区归属。

MCP 是工具接入协议，不承担任务规划、记忆或授权决策。第一版接一个受信任的只读文档检索 MCP，内置工具和 MCP 工具都经过同一执行入口。协议版本与 SDK 版本锁定；不接受用户直接注册任意服务器。远端服务使用 Streamable HTTP，凭据仅由后端管理；工具列表加载后缓存并按权限筛选，描述与输出视作不可信外部输入。错误分为协议失败与业务失败，统一映射后交给执行策略。

429/临时 5xx/网络超时采用带抖动的指数退避，额外重试最多 2 次；校验错误只允许一次参数纠正；权限拒绝不重试。并行模型调用前预留预算，结束后结算，避免并发突破预算。供应商用量缺失时保守估计并标记。

## 7. 上下文、证据、记忆与 Skills

上下文按用途分开：不可被摘要覆盖的 TaskSpec/权限；版本化计划与任务状态；最近工具交互；按需检索的证据；任务摘要。根据模型上下文窗口扣除输出预留与系统内容后计算预算，达到可用预算的 70% 时整理历史。

证据不依赖摘要保存。Evidence 包含 source_url/source_file、抓取时间、内容哈希、正文快照、片段及位置。报告中的关键结论关联 evidence_id。外部来源冲突时保存两方证据及适用条件，不能只保留模型偏好的版本。快照用于复查当时内容，URL 用于定位来源。

上传材料用标题、段落和表格语义切块，保存 document_id、chunk_id、页码/行号、hash。初始使用关键词检索与元数据过滤；数据表计算走 pandas。若评测显示同义表述导致明显漏检，再引入 pgvector 混合检索并做独立对照，避免预先引入无业务作用的向量库。

长期记忆只保存用户明确确认的偏好，如语言和图表格式，按用户隔离，可查看、修改、删除。任务临时事实不自动升格为偏好；不同用户的证据、记忆与检索均按所有者约束。

Skill 是版本化任务方法包，包含说明、适用条件、输入、步骤建议、权限需求和验收模板。首版内置 research-comparison、csv-analysis、static-report 三个受控 Skill。先按任务类型筛选，再由模型选择；按需载入。Skill 不能扩大服务端权限。成功轨迹可生成候选 Skill，但发布前需要人工检查和回归评测，不自动自我改写生效。

## 8. 验收与修复

验收按三层执行：文件/结构的确定性检查；实际运行检查；语义证据检查。Markdown 检查章节、引用映射与必需交付物；CSV 分析检查行数、字段、单位、聚合结果和异常数据处理；页面检查文件、加载、浏览器错误和约定交互。

语义审查只接收 TaskSpec、产物和来源片段，不接收执行 Agent 的自我评价。输出 criterion_id、pass/fail/unknown、evidence_refs、reason、suggested_fix。模型审查作为补充证据，不能覆盖确定性失败；存在未知项时不得宣称所有必要条件通过。

必要条件全部通过才标记 SUCCEEDED。未通过时定位受影响子任务并定向修复，重新运行相关检查及必要的回归检查；达到轮数或预算上限时进入 INCOMPLETE，保留可用产物和未完成项。验证器异常与产物不合格分别记录。

页面 JS 运行于独立来源的受限 iframe，默认禁网，禁止访问平台 Cookie。页面可预览不等于已公开部署；第一版交付静态包。

## 9. 状态、调度与恢复

Task 状态：CREATED、QUEUED、RUNNING、WAITING_INPUT、PAUSED、SUCCEEDED、INCOMPLETE、FAILED、CANCELED。执行阶段另存 phase：clarify、plan、execute、verify、repair、deliver。终态不可原地重启，重试创建关联的新 Run。

每次执行使用独立 run_id、graph_thread_id；恢复沿用同一 graph_thread_id。PostgreSQL 保存图检查点；任务表保存业务状态，两者通过运行版本和提交标记对齐，恢复时进行校验与协调，不宣称跨两套写入天然原子。

任务队列放 PostgreSQL。Worker 通过短事务和 FOR UPDATE SKIP LOCKED 领取任务，写 lease_owner、lease_until、fencing_token；执行时不持有行锁。Worker 续租，所有状态与结果提交都检查 token；超时后可重新领取。旧 Worker 即使仍在运行也不能覆盖新状态。

工具调用先记录意图，再执行，最后记录结果。幂等键为 run_id + step_id + logical_action_id；重试沿用同一键，业务重做使用新键。对本地文件采用内容哈希、版本路径与原子提交实现幂等。调用外部系统时优先使用其幂等键；对结果不明且无法查询确认的非幂等操作，停止并要求人工核对。系统承诺可恢复的至少一次调度，不承诺所有外部操作恰好一次。

检查点不能代替工作区备份：每个子任务结束时上传产物 manifest 和内容哈希。执行宿主丢失时，从最近 manifest 重建工作区；在途 Python 运算从步骤重新执行，不恢复任意进程内存。

暂停在当前受控操作结束或超时后的安全点生效；取消停止调度、向执行模块发送终止请求并标记在途结果。页面断开不停止后台任务。重新连接使用事件游标补齐状态。

## 10. 数据模型与接口

| 表 | 核心字段 |
| --- | --- |
| users | id、password_hash、created_at |
| tasks / task_specs | owner_id、status、current_spec_version；版本化契约 |
| runs | task_id、graph_thread_id、phase、lease、fencing_token、budget、usage、config_versions |
| steps | run_id、plan_version、dependencies、status、attempts、result_refs |
| tool_calls | logical_action_id、idempotency_key、intent、status、result_ref、error |
| artifacts / evidence | owner_id、run_id、object_key、hash、mime、version；来源及片段 |
| approvals | run_id、action_hash、scope、expires_at、decision |
| events | run_id、sequence、type、payload、created_at |
| skills / memories | owner_id 或受控公共范围、version、content、status |
| eval_cases / eval_runs | 输入、评分规则、固定材料、配置版本、评分与成本 |

主要接口：POST /tasks、POST /tasks/{id}/runs、GET /tasks/{id}、GET /runs/{id}/events、POST /runs/{id}/input、POST /runs/{id}/pause、POST /runs/{id}/resume、POST /runs/{id}/cancel、GET /artifacts/{id}/download。写请求使用客户端幂等键；owner_id 从服务端身份派生，禁止客户端任意指定。

事件使用 SSE，sequence 单调递增、Last-Event-ID 断线续传，事件至少一次投递，前端按 sequence 去重。状态和对应事件在同一数据库事务中保存。前端状态丢失时先读任务快照再补齐事件，防止仅靠流式文本还原状态。下载 URL 短时有效且生成前检查归属。

身份采用服务端会话与 HttpOnly/Secure/SameSite Cookie；写接口检查 CSRF。生产 HTTPS，上传限制类型、体积、表格行数及解压大小。

## 11. 隔离与信任控制

上传文件、网页正文、MCP 输出均为数据，不具有修改系统指令或扩大权限的资格。Prompt 标识数据来源，真正的权限检查由执行模块实施，不能声称仅凭提示词消除注入。

Python 与页面运行在专用执行宿主上的短生命周期环境：非 root、只读根文件系统、任务级工作区、CPU/内存/PID/时间限制、禁特权、禁挂宿主目录和 Docker socket、不注入模型密钥与平台数据库凭据。网络默认禁用。平台调用执行模块的受限接口；受信任的宿主管理进程负责容器生命周期，不向 Agent 暴露容器管理权限。

标准容器不作为公开恶意多租户的充分隔离保证。对公网开放任意用户代码执行前，执行宿主启用并验证 gVisor 或等价隔离；未完成验证时仅开放受控测试账户。执行产物交回后由可信上传模块写入存储。

抓取工具单独联网，阻止回环、私网、链路本地和云元数据地址；每次重定向和实际连接目标都校验，限制协议、响应大小、跳转数、时间与下载类型。日志脱敏，审计权限拒绝。审批绑定动作参数哈希和版本，修改参数后旧审批失效。

## 12. 评测方法

建立 45 个固定任务：研究、数据分析、静态页面各 15 个，覆盖简单、组合与异常输入；划分 30 个开发集和 15 个保留测试集。另建故障注入集，覆盖超时、429、坏工具输出、注入文本、Worker 被终止、重复领取、断线重连和来源缺失。

固定材料快照用于可重复评测，实时网络任务单独用于检查时效性，不混用两者得分。每次实验记录代码提交、模型版本、Prompt/Skill/工具版本、输入哈希和预算。多个模型版本的结果分别报告。

基线：同模型的单 Agent 工具循环。对照分别加入规划、证据检索、验收修复、并行子任务；先做单变量对照，再做组合实验。尽量统一工具权限、输入和最大预算，报告真实消耗和超预算失败，避免只比较最终答案外观。重点配置重复运行 3 次，给出样本量、均值、波动及配对结果；小样本不作显著性承诺。

主要指标：必要条件全部通过的任务比例、需求条件覆盖率、人工标注的关键结论证据支持率、产物运行通过率、故障恢复率、人工介入率、端到端延迟、每个成功任务成本、修复引入新错误比例。成本同时记录失败运行，单任务成功成本不能只统计成功样本的账单。

语义评分使用明确 rubric，并对保留集全部人工复核；模型裁判与人工不一致时记录分歧类别。不能用生成模型自己的“满意度”替代任务正确性。测试集只用于最终比较，不反复调 Prompt。

工程完成条件：权限和文件隔离测试全部通过；固定样本可完整交付三类产物；暂停恢复与故障注入有可复现记录；非幂等未知状态不会被静默重复执行；每个成功任务可追溯至契约、工具记录和验收证据。质量通过率目标在首次基线后设定，文档不预填提升数字。

## 13. 模块接口与实现组织

按职责划分 task、orchestrator、tools、sandbox、knowledge、verification、evaluation 模块，采用模块化单体加独立 Worker。公开接口尽量少：submit(spec)、resume(run_id, input)、execute(tool, args, context)、verify(spec, artifact_refs)。模型、搜索、存储和执行环境通过真实变化处的 Adapter 替换；不为每个业务函数引入抽象层。

建议目录：backend/app/{tasks,agent,tools,sandbox,knowledge,verification,evaluation}，frontend/，skills/，evals/{cases,fixtures,rubrics}，infra/，docs/。验收器、工具契约与固定评测数据先定义，随后实现状态图和执行模块，最后接前端。实现可以分批，设计与验收标准从一开始保持完整。

测试集中于契约、图分支、权限、副作用幂等、恢复与实际产物。模型单元测试使用固定结构化响应；在线模型质量进入单独评测，不让随机输出决定普通 CI 是否通过。

## 14. 关键决策记录

| 决策 | 原因 | 验证或调整依据 |
| --- | --- | --- |
| 外层状态图 + 内层自主执行 | 保持动态决策，同时限制状态与资源 | 异常输入和故障注入 |
| 单主 Agent + 有界独立子任务 | 减少通信成本，允许研究并行 | 同预算质量和延迟对照 |
| 受控 Skills + 统一工具入口 | 复用方法，集中执行权限与追踪 | 越权测试与 Skill 回归 |
| 证据持久化 + 选择性上下文 | 保留可核查事实，控制上下文体积 | 来源支持率与 Token 对照 |
| 程序检查 + 模型审查 + 有界修复 | 防止自我宣告成功和无限循环 | 修复净收益、误判与成本 |
| PostgreSQL 队列 + 租约 | 当前负载下减少基础设施 | 领取延迟与并发故障测试 |
| 不默认向量库或长期自动记忆 | 检索与偏好有明确用途再引入复杂性 | 检索漏召回与记忆污染评测 |
