# 云端 Agent 工作台技术方案

状态：执行路线已确认，详细方案继续收敛。用户确认保留 Python 平台并复用成熟执行器的 Agent loop，依据 [ADR-0002](adr/0002-reuse-agent-harnesses.md)。旧方案保留在[原生循环历史稿](技术方案-原生循环历史稿.md)，不作为当前实现要求。

## 1. 已确认架构

平台负责产品工作流，Claude Code 与 Codex 承担原生 Agent 执行。Python/FastAPI 作为控制面，React/TypeScript 作为工作台；执行器通过适配层接入平台管理的云端环境。

```text
用户工作台
    │
Python/FastAPI：项目、任务、双模式、阶段与人工确认
    │
执行器适配层：身份映射、配置、事件、审批、停止、恢复
    ├── Claude Code：Agent SDK
    └── Codex：App Server 双向协议
             │
       原生 Agent loop
             │
    原生工具 / 平台 MCP / 云端工作空间
```

执行器负责内层模型决策与工具循环；平台负责约束工作、协调结果并判断是否交付。平台进程、执行器运行、用户代码和凭据的实际隔离方式由工作空间决策确定，图中连线不表示它们应共享宿主权限。

## 2. 技术栈与尚未决定事项

| 范围 | 当前决定 |
| --- | --- |
| 后端 | Python、FastAPI |
| 前端 | React、TypeScript |
| 首批执行器 | Claude Code、Codex |
| Claude Code 集成 | 官方 Agent SDK Python 接口，具体版本锁定并验证 |
| Codex 集成 | 官方 App Server 双向 JSON-RPC，优先使用 stdio 受控接入 |
| 外层阶段编排 | 独立于内层 loop；LangGraph 保留为候选，状态决策后确定 |
| 业务存储与事件 | 尚待一致性设计；PostgreSQL 为候选，不视为整个存储方案已批准 |
| 队列与 Worker | 尚待消息、租约与恢复决策 |
| 云端环境 | 自管增强隔离与托管沙箱已经研究，具体路线尚待选择 |

复用原生执行器不要求移植参考项目的桌面客户端。执行器与模型分别选择，供应商认证和模型可用性须按对应执行器验证。

## 3. 模块 Interface 与所有权

| Module | 拥有的产品行为 | 对外结果 |
| --- | --- | --- |
| 任务编排 | 自由/需求开发模式、版本、队列、阶段 Skill、确认、完成条件 | 接收、等待、执行、阶段与交付状态 |
| 执行器适配 | 云端进程与原生会话管理、输入、交互、停止与事件映射 | 标准执行事件与真实原生标识 |
| 工具与扩展 | 安装、MCP 配置、项目作用域、凭据、权限与撤销 | 已授权且配置就绪的能力及有效版本 |
| 协作管理 | 主 Agent、持久成员、指派、汇报和总预算 | 成员状态及交付依据 |
| 记忆与个性化 | 平台长期指令、项目记忆与可见修订 | 受作用域限制的索引、内容与配置 |
| 成果与验收 | 真实文件、版本、证据、检查及人工验收 | 可下载、可预览和可解释的结果 |

模块采用清晰 Interface，不因职责拆分就强制微服务化。必须保存平台 task/run/member 与执行器 session/thread/turn 的映射及执行器版本和认证作用域，不能把同一字符串当作所有层级身份。

## 4. 两种模式如何使用同一执行器层

自由模式把目标、用户选择的 Skill 与允许的工具交给执行器。平台处理其公开事件、提问、权限请求和结果，并按用户设置的确认点和交付条件收尾。

需求开发模式先由平台确定当前阶段、输入、阶段 Skill 与允许动作，再让执行器执行本阶段工作。阶段返回后检查成果和版本，在需求基线、方案与最终验收等人工确认点等待；确认有效后才发起下一阶段执行。

七阶段仍为需求澄清、方案设计、任务拆解、开发实现、测试与修复、验收评审、成果交付。原生轮次完成只说明该次执行到达其终态，不直接等于阶段通过或需求完成。

## 5. 执行器 Adapter 契约

共同 Interface 覆盖查询能力与认证状态、创建/恢复、投递输入、响应交互、请求停止/关闭、读取执行事件。每个 Adapter 单独实现原生协议，不依赖终端界面文本来猜测完成情况。

- Claude Code：复用官方 SDK 的会话、输入流、工具权限与中断能力，转换为平台事件与确认卡。
- Codex：握手后使用 thread/start/resume 与 turn/start 等接口；中断、原生审批和流式事件按该版本协议处理。
- 立即纠正以真实接收回执为准，不支持时按产品规则返回可解释结果。
- 原生终态需区分 completed、interrupted 与 failed 等语义，不能只看进程退出码。
- 普通输入的持久队列属于平台；原生会话是否支持恢复、分叉、改变模型和供应商由对应能力决定。

跨执行器默认是新原生会话加显式交接，不把一种执行器的会话标识传给另一种。辅助命名、审查等单次模型任务可以使用客户端 SDK，这不构成平台重新拥有内层工具循环。

## 6. 工具权限、Skills 与记忆

执行器原生工具和平台 MCP 都必须受权限约束。审批回调、自动允许名单和前置钩子之间的实际顺序需要逐执行器验证，不能因为配置了回调就断言一切原生工具都经过平台审批。无法满足强制约束的能力不开放。

阶段 Skill、用户方法和长期指令由平台保存，并按对应执行器的实际加载机制生成配置快照。记录已安装、项目启用、本次已加载的区别；更新不能静默冒充已经影响当前原生会话。

项目记忆由平台管理并可经受控工具供执行器读写。原生自动记忆、配置目录及历史存储应有明确作用域，防止与平台记忆重复或跨用户、项目传播。关闭平台记忆不等于清除执行器已经加载的上下文。

## 7. 协作与文件

持久成员各自对应独立原生会话，可使用不同执行器。平台保存成员身份与分工，消息有稳定指派标识和派发回执；原生临时子 Agent 作为不同执行渠道记录。

项目共享材料，成员在独立修改区形成结果，主 Agent 检查基线与冲突后应用。原生工具能够写文件不代表可以绕过共享文件规则；具体目录、分支或快照机制由工作空间决策确定。

停止整个任务覆盖所有平台成员及可管理的原生子执行，保留并暂停未派发要求。不能用其中一个执行器的完成结果替代其他成员的终态。

## 8. 持久化与恢复原则

平台待确认事项、需求和成果版本、指派、权限、取消意图及预算必须独立可恢复。原生 session/thread 恢复只解决对应执行器的上下文，不自动重建项目文件、平台状态和认证。

分别处理文件持久化、原生会话持久化、进程存活及执行结果记账。发生结果不明时先核对，不能盲目重复有副作用的原生工具动作。检查点、原生 rollout 或进程快照均不单独保证恰好一次执行。

## 9. 实现切片与验证

更新后的[任务拆分草案](实现任务拆分草案.md)先交付首个执行器端到端会话与工具产物，再通过独立切片接入第二执行器；阶段流程、扩展和协作在共同 Interface 上扩展。草案尚未作为正式实现工单发布。

验证包括执行器协议与事件夹具、真实 SDK/CLI 集成、原生工具与 MCP 两条权限路径、停止和恢复竞态、跨引擎交接、阶段确认版本及云端隔离。夹具不替代实际执行器验证，原生轮次成功不替代用户验收。
